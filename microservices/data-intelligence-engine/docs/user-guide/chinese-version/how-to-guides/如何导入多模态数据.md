# 如何摄取多模态数据

如需摄取比[快速入门](../快速开始.md)中的文本文件更多种类的文件
（PDF、图像、视频、音频或 OKF 知识包(knowledge bundle)），请按照本指南操作。本指南
承接该部署：引擎运行在 `http://localhost:16022`，并已将 Milvus 注册为
`local-milvus`。每种内容类型都遵循相同的步骤：准备其模型、创建源(source)和池(pool)、
摄取(ingest)，然后检索(retrieve)。

请在 `data-intelligence-engine/scripts` 目录下运行命令。脚本自身会对 `localhost` 绕过
代理；如果在代理环境下执行下文的 `curl` 调用，请先运行
`export no_proxy=localhost,127.0.0.1,$no_proxy`。

<a id="1-prepare-models"></a>
## 1. 准备模型

引擎在运行时从不下载或转换模型。首次运行时，
`quickstart.sh` 会准备本指南用到的所有模型：GME、bge-reranker-large、
PP-DocLayoutV3、ViCLIP-B、Whisper 以及 Qwen3-VL INT8 媒体重排模型。如果你的
模型是在此之前准备的，或者你想使用 ViCLIP-L 等替代模型，
请用 `prepare-models.sh` 添加，它会跳过已就位的模型：

```bash
./prepare-models.sh                    # 默认模型集
./prepare-models.sh viclip-l           # 替代视频模型
```

各模型详见[如何准备模型](如何准备模型.md)。下文路径
均相对于 `data-intelligence-engine/workspace/models/`。通过
`operator_options.embedding_model` 选择已准备好的模型包：本地模型 ID 对应
该根目录下的目录名，每种权重变体都有各自的模型 ID。

| 数据 | 模型 / 索引内容 | 准备目录 |
|---|---|---|
| 视频 | ViCLIP-B（`viclip-b-fp16`，默认）、ViCLIP-L 或 Cosmos-224p，原始视频 | `viclip-b-fp16/`、`viclip-l-fp16/` 或 `cosmos-224p-fp16/`；每个也都支持 `fp32` 包 |
| 图像 / 视频描述 | GME-Qwen2-VL-2B，像素 / 派生的描述(caption)文本 | `gme-Qwen2-VL-2B-Instruct-OV/` |
| 音频 | Whisper-small → GME，转写文本 | `whisper-small/` + 上述 GME |
| PDF / OKF 文档语料 | 原生 GME，文档文本和 PDF 插图 | 上述 GME；PDF 还需要 `PP-DocLayoutV3/pp_doclayout_v3.onnx` |

扫描版 PDF 使用 Tesseract 读取，引擎镜像已内置 Tesseract 及其
中文和英文数据。

<a id="2-create-a-library"></a>
## 2. 创建知识库

```bash
./library.sh create '{"name":"my-library"}'
```

知识库(library)存放资产(asset)，源(source)指定向量写入何处，池(pool)则将资产绑定
到源。如果你不是通过 `quickstart.sh`，而是在本地 Python 环境中运行引擎，
请先以 URI `http://localhost:19530` 将 Milvus 注册为 `local-milvus`
（参见[数据库 API](../../api.md#databases)）。

<a id="3-source-options"></a>
## 3. 源选项

`operator_options` 属于源的创建参数，而非摄取请求的参数。

| 字段 | 是否必需 | 用途 / 默认值 |
|---|---|---|
| `asset_types` | **独立媒体必需** | 非空数组：`["video"]`、`["image"]` 或 `["audio"]`。`["mp4"]` 等扩展名/MIME 类型可缩小文件范围。对文档可选（`["document"]`，文本源的默认值）；图谱源默认为 `["okf"]`。 |
| `block_roles` | 否 | 选择表示形式。省略时：视频 → 原始视频，图像 → 像素，音频 → `l2_transcript`。对视频设置 `["l2_caption"]` 则选择 GME 描述文本。`[]` 表示不添加角色过滤。 |
| `block_kinds` | 否 | 高级块过滤器，**不是**模型选择器。省略时：由表示形式推导；`[]` 表示不添加类型过滤。必须与表示形式/模型兼容。 |
| `embedding_model` | 否 | 按 ID 选择 `ENGINE_MODEL_ROOT_PATH` 下已准备好的模型。省略时：使用该类别的默认模型。每种权重变体使用单独的模型 ID。必须支持所选的表示形式。 |
| `embedding_backend` / `embedding_device` | 否 | 覆盖运行时 / 设备；否则使用该模型类别的引擎默认值。 |
| `max_image_tokens` | 否 | GME 视觉 token 上限；默认取模型包中的设置。 |
| `frames_per_clip` | 否 | 所有视频模型固定为 `8`；必须与模型包一致。 |
| `chunk_size` / `chunk_overlap` / `figure_context_chars` | 否 | 文档分块及 PDF 插图上下文；使用引擎默认值。 |

- 一个源 = 一个固定的模型/向量空间。视频像素和描述应使用不同的源和集合(collection)。
  过滤器只负责选择内容，不会生成内容。
- 在默认设置下，文档/PDF 和已有 OKF 的摄取均无需 `operator_options`。

<a id="4-ingest-files"></a>
## 4. 摄取文件

只需运行所需的小节。每个小节都遵循 **源 → 池 → 摄取** 的顺序。
`assets.sh add` 通过引擎 API 上传文件或文件夹；普通文件夹会
摄取其中受支持的文件。重新摄取某个文件会替换其向量，因此重复
运行不会产生重复数据。`--wait` 等待的是资产物化(materialization)完成，
**而不是**描述生成/转写或所有源同步的完成；参见
[检查状态](#5-check-status)。

<a id="videos"></a>
### 视频

ViCLIP-B 对时长已知且 ≤ 60 秒的视频以及已有的 `l1_segment` 块进行嵌入(embedding)，
每个向量采样八帧；查询则由其自带的文本编码器进行嵌入。较长
或时长未知的视频会被存储但不会被覆盖；引擎不会对其进行切分。

```bash
./sources.sh create my-library '{
  "name":"video-viclip-b",
  "database_id":"local-milvus",
  "collection_name":"my_library_video_viclip_b",
  "operator_options":{"asset_types":["video"],"embedding_model":"viclip-b-fp16"}
}'
./pools.sh create my-library '{
  "id":"video-segments","name":"Videos","sources":["video-viclip-b"]
}'
./assets.sh add my-library ../data/videos/my_video_segments \
  --pool video-segments --wait
```

如需使用 Cosmos，请设置 `"embedding_model":"cosmos-224p-fp16"` 并使用单独的集合。

可选：并行索引**同一批资产**的描述，无需重新上传，
也无需替换视频编码器。在启动引擎之前，于 `deployment/docker/.env` 中将
`ENGINE_VIDEO_SUMMARY_BASE_URL` 设置为一个已在运行的描述服务；
此集成尚未经过端到端验证。

```bash
./sources.sh create my-library '{
  "name":"video-caption-gme",
  "database_id":"local-milvus",
  "collection_name":"my_library_video_caption_gme",
  "operator_options":{"asset_types":["video"],"block_roles":["l2_caption"],"embedding_model":"gme-Qwen2-VL-2B-Instruct-OV"}
}'
./pools.sh add-sources my-library video-segments video-caption-gme
```

描述更新只会重新同步使用描述的源，而不会影响 ViCLIP 视频向量。

<a id="images"></a>
### 图像

GME 将文本和图像置于同一向量空间，因此文本查询可以找到图片。挂载
源时会加载模型（在 CPU 上使用 int8 权重约需 5 秒）；之后每张图像
在 CPU 上约需 1-2 秒。`max_image_tokens` 是影响延迟的主要参数。

```bash
./sources.sh create my-library '{
  "name":"image-gme-embeddings",
  "database_id":"local-milvus",
  "collection_name":"my_library_image_gme",
  "operator_options":{"asset_types":["image"],"embedding_model":"gme-Qwen2-VL-2B-Instruct-OV"}
}'
./pools.sh create my-library '{
  "id":"images","name":"Images","sources":["image-gme-embeddings"]
}'
./assets.sh add my-library ../data/images --pool images --wait
```

<a id="audio"></a>
### 音频

摄取完成后，Whisper 会在后台转写每段录音，GME 对转写文本
进行嵌入，而非原始音频。默认语言为普通话；如需其他语言，
请在 `deployment/docker/.env` 中设置 `ENGINE_ASR_LANGUAGE`（例如 `en`），并重新运行
`quickstart.sh` 以重建引擎容器。

```bash
./sources.sh create my-library '{
  "name":"audio-gme",
  "database_id":"local-milvus",
  "collection_name":"my_library_audio_gme",
  "operator_options":{"asset_types":["audio"],"embedding_model":"gme-Qwen2-VL-2B-Instruct-OV"}
}'
./pools.sh create my-library '{"id":"audio","name":"Audio","sources":["audio-gme"]}'
./assets.sh add my-library ../data/audio/my_recordings --pool audio --wait
```

当某段录音的 `/enrichment` 报告 `transcript_status:
completed` 且 `embedding_status: ready` 时即可被检索（参见[检查状态](#5-check-status)）。
每段不超过 30 秒、在停顿处切分的语音为一条结果，带有
`t_start_ms` 和 `t_end_ms`。

<a id="pdfs"></a>
### PDF

默认的原生 GME 处理文本块和提取出的插图，插图会连同其引用文本
一起嵌入；PP-DocLayoutV3 负责检测插图，没有它则无法读取扫描版 PDF。
PDF 属于文档，因此源使用 `"asset_types":["document"]`，这也是默认值；
进行通用文档摄取时可省略 `operator_options`。

```bash
./sources.sh create my-library '{
  "name":"pdf-gme",
  "database_id":"local-milvus",
  "collection_name":"my_library_pdf_gme",
  "operator_options":{"asset_types":["document"],"embedding_model":"gme-Qwen2-VL-2B-Instruct-OV"}
}'
./pools.sh create my-library '{
  "id":"pdf-documents","name":"PDFs","sources":["pdf-gme"]
}'
./assets.sh add my-library ../data/mmdir/my_pdfs --pool pdf-documents --wait
```

数字版 PDF 的文本会在其插图处理完成之前即可被检索；资产的
`materialization` 会从 `text_ready` 变为 `ready`。请将此文档源与
独立图像源分开，以免同一张提取出的插图被索引两次。

<a id="okf-knowledge-graphs"></a>
### OKF 知识图谱

将已有的 OKF 概念包(concept bundle)与其原始文档一起摄取。此操作
不会从文档中抽取 OKF。

```text
data/okf/my_dataset/
├── corpus/          # 原始文档；保留 source_files 所引用的路径
│   ├── doctors/
│   ├── records/
│   └── residents/
└── okf_bundle/      # 一个 OKF 资产：index.md + 各概念子目录
    ├── index.md
    ├── doctor/
    └── resident/
```

Milvus 存放文档/概念向量，NebulaGraph 存放概念及其链接。
请将两个源、完整的语料和概念包放在**同一个池**中。启动
NebulaGraph 并注册它；引擎容器通过共享网络上的服务名
访问它：

```bash
docker compose -f ../deployment/docker/docker-compose-nebula.yml up -d
curl -X POST http://localhost:16022/v1/databases -H 'Content-Type: application/json' -d '{
  "id":"local-nebula","type":"graph","backend":"nebula",
  "options":{"url":"nebula://nebula-graphd:9669"}}'
curl -X POST http://localhost:16022/v1/databases/local-nebula/check
```

检查返回 `reachable: true` 后再继续。`username` 默认为 `root`；
当 Nebula 的授权处于禁用状态（本套部署的默认设置）时，可以省略 `password`；
否则请将两者都添加到 `options` 中。请使用客户端端口
`9669`；`19669` 仅用于 HTTP 状态检查。

```bash
./library.sh create '{"name":"knowledge-library"}'
./sources.sh create knowledge-library '{
  "name":"knowledge-text","database_id":"local-milvus",
  "collection_name":"my_knowledge_text_gme"
}'
./sources.sh create knowledge-library '{
  "name":"knowledge-graph","database_id":"local-nebula",
  "collection_name":"my_knowledge_concepts"
}'
./pools.sh create knowledge-library '{
  "id":"knowledge-documents","name":"Knowledge",
  "sources":["knowledge-text","knowledge-graph"]
}'
./assets.sh add knowledge-library \
  ../data/okf/my_dataset/corpus ../data/okf/my_dataset/okf_bundle \
  --pool knowledge-documents --wait
```

如上所示，将 `corpus` 和 `okf_bundle` 作为目录上传：每个受支持的文档
对应一个资产，另加一个通过其 `index.md` 识别的概念包资产。不要
将语料扁平化，也不要只上传 `index.md`。两个源都完成同步后，
查看图谱：

```bash
./pools.sh read knowledge-library knowledge-documents \
  | jq '.source_statuses[] | {source_id, status, serving_state, error}'
./pools.sh graph knowledge-library knowledge-documents 20
```

<a id="5-check-status"></a>
## 5. 检查状态

摄取返回 `202` / `materializing`。空池也可能已报告就绪；
请检查资产和源同步状态，必要时再检查媒体增强(enrichment)状态。

```bash
./assets.sh read my-library 1 1000 \
  | jq '.assets[] | {id, name, materialization}'
./pools.sh read my-library video-segments \
  | jq '.source_statuses[] | {source_id, status, serving_state, error}'
./pools.sh routing my-library video-segments

ASSET_ID="<asset-id-from-list>"
curl -sS "http://localhost:16022/v1/libraries/my-library/assets/$ASSET_ID/enrichment" \
  | jq '{caption_status, transcript_status, embedding_status, embedding_reason}'
```

| 检查项 | 就绪条件 / 处理方式 |
|---|---|
| 资产 `materialization` | `ready` |
| 所需源的同步 | `status: ready`、`serving_state: SERVING`，且无错误；若为 `failed`，请查看 `error` |
| 媒体 `embedding_status` | `ready`；若为 `no_source` / `failed`，请查看 `embedding_reason` |
| 描述 / 转写 | 需要时单独检查；未配置描述服务时，描述为 `skipped` 属正常情况 |

<a id="6-retrieve"></a>
## 6. 检索

```bash
./retrieve.sh query my-library "a person sitting up in bed" \
  --pool video-segments --type vectorsimilarity --top-k 3
./retrieve.sh query my-library "a nurse bringing water" \
  --pool images --type vectorsimilarity --top-k 3
./retrieve.sh query my-library "What does the architecture diagram show?" \
  --pool pdf-documents --type vectorsimilarity --top-k 5
./retrieve.sh query knowledge-library "Which doctor is responsible for resident 001?" \
  --pool knowledge-documents --type rrf --top-k 10 --trace
```

重复使用 `--pool` 可检索多个池，省略则检索整个知识库。
对于 OKF，`--type graph` 只显示图谱分支及其回溯到文档
块的追踪信息。以下是在 Python 中进行同样的调用（与检索器(retriever)的调用方式一致）：

```python
import httpx

response = httpx.post(
    "http://localhost:16022/v1/retrieve",
    json={"query": "a person sitting up in bed", "libraries": ["my-library"], "top_k": 3},
    timeout=60,
)
response.raise_for_status()
for chunk in response.json()["chunks"]:
    print(f'{chunk["score"]:.3f}  {chunk["metadata"]["file_name"]}')
```

- **结果**：视频、图像、转写文本块、PDF 文本/插图，或被 OKF 概念
  引用的文档块。`source_id` 标识源，`pool_id` 标识池。
- **分数**：各向量源独立检索，每个源最多取 `top_k` 个
  候选，再将各列表以轮询(round-robin)方式交错合并。不同模型之间的分数
  未经校准，因此请使用单独的池分别查看各模型的排序，
  或进行重排(reranking)（见下文）。
- **OKF**：结果是带有图谱追踪信息的文档块，而非生成的答案。
  缺少文档块通常意味着完整语料缺失、其路径
  发生了变化，或文本同步尚未完成。图谱检索只使用第一个
  处于服务状态的文本源；替换该源目前尚不会迁移图谱溯源信息或
  概念索引。

<a id="7-media-reranking"></a>
## 7. 媒体重排

在媒体请求中添加 `"postprocess":{"processor_type":"reranker","top_n":3}`；
Qwen3-VL INT8 媒体重排模型属于默认模型之一。
`top_k` 控制每个源的候选数量；`top_n` 限制最终全局排序的结果数。
如果没有可用的 GPU，请运行 `quickstart.sh --cpu`（在没有 `/dev/dri` 的主机上会自动启用）；
如果只想迁移媒体重排模型，请在 `deployment/docker/.env` 中设置
`ENGINE_MEDIA_RERANK_DEVICE=CPU`，并重新运行 `quickstart.sh`。示例、
模型选项和失败行为请参见[媒体重排](../../text-to-media-retrieval.md#media-reranking)。

<a id="notes"></a>
## 注意事项

- **视频限制**：视频嵌入不覆盖超过 60 秒的片段。请检查
  `/enrichment` 以了解缺失的覆盖情况。
- **GME 内存**：文档源和图像源只有在使用相同模型包、设备和 `max_image_tokens` 时
  才会共享同一运行时。两者默认都使用 GPU（使用 `quickstart.sh --cpu` 时为 CPU）；
  如果你覆盖了其中一个的设备，请让另一个保持一致，以免加载两份模型副本。
- **模型错误**：如果挂载源时返回 `503`，请检查错误信息中是否有
  缺失的模型文件或错误的路径；参见
  [挂载源失败时](../../user-guide.md#when-attaching-a-source-fails)。
- **更换模型**：源的模型在创建时即已固定；如需切换，请按
  [附录：替换源](#appendix-replace-a-source)替换该源。

<a id="appendix-inspect-data-with-web-uis-for-dev"></a>
## 附录：使用 Web UI 查看数据（开发用）

<a id="milvus-attu"></a>
### Milvus (Attu)

Milvus 没有内置 UI。Attu 是它的 Web 控制台，其版本必须与 Milvus 匹配。本套部署运行的是 Milvus v2.4.x，因此请使用 Attu v2.4.x。`latest` 标签只能连接 Milvus 2.6 及更高版本。

```bash
docker run -d --name attu --restart unless-stopped \
  --network data-intelligence-network -p 33000:3000 zilliz/attu:v2.4.12
```

打开 `http://<host>:33000`，使用地址 `milvus-standalone:19530` 并将认证方式设为 **None** 进行连接。
请使用容器网络中的服务名，而不是 `localhost`。
你的集合（`my_library_video_viclip_b`）中每个视频片段对应一条 512 维的记录，字段如上文所述。

<a id="nebulagraph-studio"></a>
### NebulaGraph (Studio)

- **启动**：Studio 是一个独立的 Web 控制台。Studio v3.8.0 支持本套部署的
  NebulaGraph v3.6.0。请先[启动 NebulaGraph](#okf-knowledge-graphs)，
  然后在同一 Docker 网络上运行 Studio：

```bash
docker run -d --name nebula-studio --restart unless-stopped \
  --network data-intelligence-network -p 7001:7001 \
  vesoft/nebula-graph-studio:v3.8.0
```

- **连接**：打开 `http://<host>:7001`；输入 `nebula-graphd:9669`、用户名
  `root` 以及任意密码（授权已禁用）。不要使用 `localhost` 或 `nebula://` 前缀。
  端口 `19669` 用于状态检查，而非 Studio。授权默认处于
  禁用状态；请勿将此开发环境暴露到公共网络。
- **等待数据就绪，而不是等网页打开**：Studio 可能在摄取
  完成之前就已能打开。`reachable: true` 仅确认数据库可连通。对于这次
  初始 OKF 摄取，请等待以下条件满足：
  - 所有返回的资产均已注册，且 `materialization: ready`。
  - `knowledge-text` 和 `knowledge-graph` 均报告 `status: ready`、
    `serving_state: SERVING` 和 `error: null`。
  - 对于包含链接的概念包，池图谱查询能返回节点和边。
    空池同样可能报告 `ready`，因此还要检查资产和图谱。

```bash
# 在 data-intelligence-engine/scripts 下运行；摄取进行期间可重复执行读取命令。
./assets.sh read knowledge-library 1 1000 \
  | jq '.assets[] | {name, materialization}'
./pools.sh read knowledge-library knowledge-documents \
  | jq '.source_statuses[] | {source_id, status, serving_state, error}'
# 上述检查通过后，验证图谱内容。
./pools.sh graph knowledge-library knowledge-documents 20
```

- **首次构建耗时**：语料分块/嵌入会先于 OKF 图谱写入
  和概念嵌入执行；Nebula 还需等待 space/schema 传播完成。目前
  没有实测的端到端预计耗时。在 CPU 上处理数百个文档时，根据分块数量和硬件情况，
  需预留数十分钟或更长时间。`knowledge-text:
  indexing` 同时 `knowledge-graph: pending` 表示图谱阶段正在等待
  文本同步。出现 `failed` 状态时需要检查 `error`，继续等待无济于事。
- **查看**：选择 space `my_knowledge_concepts`（即图谱源的
  `collection_name`）。**Schema** 显示的是 tag/edge 定义，并不会自动
  呈现已填充数据的图。请在 **Console** 中运行以下查询来查看记录：

```ngql
SHOW SPACES;
USE my_knowledge_concepts;
SHOW TAGS;
SHOW EDGES;
MATCH (v) RETURN v LIMIT 10;
MATCH p=(a)-[e]->(b) RETURN p LIMIT 10;
```

- **空结果与空白页**：space/结果为空可能意味着摄取尚未完成，或
  选错了 space。浏览器页面完全空白则是 UI 加载问题，
  并不代表图谱是否就绪；请检查 Studio 的日志和浏览器报错。

```bash
docker logs --tail 50 nebula-studio
curl -I http://localhost:7001/
```

- **存储**：Nebula 存放概念和链接；文档块和概念
  向量保存在 Milvus 中。[官方 Studio 部署指南](https://docs.nebula-graph.io/3.6.0/nebula-studio/deploy-connect/st-ug-deploy/#docker-based_studio)。

<a id="minio"></a>
### MinIO

默认情况下 MinIO 的端口不会发布到主机；控制台在 `data-intelligence-network` 内监听 `MINIO_CONSOLE_PORT`（`9001`）。如需打开 `http://<host>:9001`，请发布该端口，例如为 `minio` 服务添加 `ports: ["9001:9001"]`。使用 compose 默认凭据 `minioadmin` / `minioadmin` 登录。任何共享部署都请修改这些凭据。
端口取自 `data-intelligence-engine/deployment/docker/.env` 中的 `MINIO_API_PORT` 和 `MINIO_CONSOLE_PORT`。

此 MinIO 是 Milvus 的内部存储。`a-bucket` 存放的是 Milvus 段文件和索引数据，而不是你的视频。
默认情况下，引擎将内容记录保存在文件系统的 `data-intelligence-engine/workspace/content/` 下，视频则保存在 `data-intelligence-engine/workspace/uploads/<library-id>/` 中：

```bash
ls data-intelligence-engine/workspace/content/*/assets    # 每个资产一条 JSON 内容记录
ls data-intelligence-engine/workspace/uploads/*/          # 视频文件本身
```

<a id="appendix-replace-a-source"></a>
## 附录：替换源

源的模型和参数在创建时即已固定；只有其嵌入设备
可以原地更改（使用 `{"embedding_device":"CPU"}` 调用 `PATCH /{library}/sources/{source_id}`，
会在新设备上重新嵌入该源的记录，
媒体则从其存储的 blob 重新嵌入；在 GPU 之间迁移（如 `GPU.0` 到 `GPU.1`）
会保留向量）。若要使用其他检查点(checkpoint)或
权重变体，则需新建一个指定不同已准备模型 ID 的源，并在池中替换
旧源。无需重新摄取；旧向量会一直保留，直到被删除。

示例：从 `viclip-b-fp16`（512 维）切换到单独准备的
`viclip-l-fp16` 包（768 维）；参见
[视频模型准备](如何准备模型.md#45-viclip-short-videos)。
请为新的向量空间使用**新的集合**。

切换前，先检查各类内容由哪个源负责：
```bash
./pools.sh routing my-library video-segments
```

```bash
# 1. 新建源和集合。embedding_model 用于选择已准备好的模型包。
./sources.sh create my-library '{
  "name":"video-viclip-l",
  "database_id":"local-milvus",
  "collection_name":"my_library_video_viclip_l",
  "operator_options":{"asset_types":["video"],"embedding_model":"viclip-l-fp16"}
}'

# 2. 挂载新源，替换 video-viclip-b
./pools.sh add-sources my-library video-segments video-viclip-l --replaces video-viclip-b

# 3. 观察切换过程
./pools.sh read my-library video-segments \
  | jq '.source_statuses[] | {source_id, status, serving_state}'
```

之后再次检查路由——此时应由新源负责 `short_video`：
```bash
./pools.sh routing my-library video-segments
```

- 新源处于 `PREPARING` 状态期间，池继续由旧源提供结果。
- 新源对所有资产完成重新嵌入后，会变为 `SERVING`，旧源则变为 `DEGRADE`——其向量保留在 Milvus 中，其模型会被卸载。
- 回滚只需反向执行同样的命令：重新挂载 `video-viclip-b`，并指定 `--replaces video-viclip-l`。

控制台会在 Sources 列表和画布(canvas)检查器中按池显示
`serving_state`。选择 `DEGRADE` 可停用该绑定，选择 `SERVING` 可恢复；
其已存储的向量会被保留。恢复后的源在就绪之前会在池中报告 `PREPARING`。
此操作不会替换或停止其他源；如需协调替换，请使用上文的 `--replaces`。
若在画布中删除连线，则会解除该绑定。

即使是同一检查点的不同权重变体，也可能产生不同的分数；
新源会先重建向量再接管服务。同样的流程也适用于
不同的检查点。所有受支持的视频模型包都将 `frames_per_clip`
固定为八；若不匹配，挂载时会被拒绝。

图像也同样适用：准备一个单独的
`gme-Qwen2-VL-2B-Instruct-OV-int4` 包（使用
`scripts/export_gme_ov.py --precision int4 --output-dir <model-root>/gme-Qwen2-VL-2B-Instruct-OV-int4`；
`prepare-models.sh` 始终写入 `gme-Qwen2-VL-2B-Instruct-OV/`），使用
`"embedding_model":"gme-Qwen2-VL-2B-Instruct-OV-int4"` 创建一个源，然后替换
`image-gme-embeddings`。

各模型的存放位置以及如何转换或检查模型：[如何准备嵌入模型](如何准备模型.md)。

<a id="appendix-delete-ingested-data"></a>
## 附录：删除已摄取的数据

删除源只会删除引擎的配置；其集合和向量仍会保留。删除池还会删除该源下不被其他任何池持有的资产的向量；资产和文件仍会保留。
删除知识库会删除其全部资产（向量、内容记录以及 `uploads/` 中的文件）、池和内容目录。Milvus 没有用于删除集合的引擎 API。

| 删除对象 | 运行 | Milvus 中的向量 | 媒体文件 |
|---|---|---|---|
| 部分资产 | `assets.sh delete-one` / `delete` | 删除 | 删除内容记录；若文件位于 `workspace/uploads/` 中，文件也会被删除 |
| 池 | `pools.sh delete` | 删除仅属于该池的资产的向量 | 保留 |
| 源 | `sources.sh delete` | **保留**（集合仍在） | 保留 |
| 知识库 | `library.sh delete` | 删除 | 删除内容记录；若文件位于 `workspace/uploads/` 中，文件也会被删除 |
| Milvus 集合 | `pymilvus` 或 Attu | 删除 | 保留 |

请在 `data-intelligence-engine/scripts` 下运行这些命令。

<a id="remove-some-assets"></a>
### 删除部分资产

```bash
./assets.sh delete-one my-library <asset-name-or-id>
```

如需删除多个资产，请将 `{"asset_ids": ["<id>", "<id>"]}` 写入文件，然后运行 `./assets.sh delete my-library @file.json`。
可通过 `./pools.sh assets my-library video-segments` 查找 id。
重新摄取已删除的文件等同于一次全新摄取，但删除资产时已将该文件从 `uploads/` 中删除，因此需要用 `assets.sh create` 重新暂存该文件。
从 `uploads/` 之外的绝对路径摄取的文件会保留在原处。

<a id="remove-everything-for-one-library"></a>
### 删除某个知识库的全部内容

`library.sh delete` 会删除该知识库的资产（向量、内容记录和已上传的文件）、池和内容目录。
各源的 Milvus 集合仍会保留；之后请使用 pymilvus 或 Attu 删除它们。

```bash
LIB=my-library

# 1. 知识库及其资产、池和内容目录
./library.sh delete $LIB

# 2. 现已为空的 Milvus 集合，使用引擎镜像中的 pymilvus 删除
docker exec data-intelligence-engine python -c 'from pymilvus import MilvusClient
MilvusClient(uri="http://milvus-standalone:19530").drop_collection("my_library_video_viclip_b")'
```

跳过第 2 步可保留空集合。从 `uploads/` 之外的绝对路径摄取的文件会保留在原处。
在 Attu 的 Collections 页面中删除集合与第 2 步效果相同。

<a id="reset-the-whole-dev-environment"></a>
### 重置整个开发环境

此操作会删除所有知识库、所有向量和全部上传文件，但会保留已准备好的模型。

```bash
cd data-intelligence-engine
scripts/quickstart.sh --down
sudo sh -c 'rm -rf workspace/milvus/*/* workspace/content/* workspace/uploads/* workspace/configs/*.json'
```

如果你启动了 NebulaGraph，`quickstart.sh --down` 不会停止它；还需运行
`docker compose -f deployment/docker/docker-compose-nebula.yml down`，并在 `rm` 中加上 `workspace/nebula/*`。

这里由 `sudo` 启动 shell，以便通配符以 root 身份展开：Milvus 的 `etcd` 和 `minio` 文件夹对你的用户不可读，而引擎容器以你的用户身份（`USER_UID`）写入。
只删除了目录中的内容，因此文件夹本身仍然保留，你无需重复执行[启动服务](../快速开始.md#step-1-deploy)中的 `mkdir`。
使用 `scripts/quickstart.sh` 重新启动服务，它也会重新注册 Milvus。

<a id="appendix-the-engine-workspace-for-dev"></a>
## 附录：引擎工作区（开发用）

引擎保存的所有内容都位于 `data-intelligence-engine/workspace/` 下，该目录以与主机上相同的路径挂载到引擎容器中（`quickstart.sh` 会设置 `ENGINE_WORKSPACE_CONTAINER_PATH`；仅当其未设置时才挂载为 `/workspace`）。在清理某个目录之前，请先了解是谁在写入它。

| 目录 | 内容 | 写入方 | 读取方 |
|---|---|---|---|
| `configs/` | `asset_library.json`（知识库、源、池、资产）和 `databases.json`（连接） | 引擎，每次变更时写入 | 引擎启动时读取 |
| `content/<library-id>/assets/` | 每个资产一条 JSON 内容记录：包括其元数据、描述以及指向媒体的指针 | 引擎在摄取时写入，描述生成后再次写入 | 引擎在索引、生成描述和检索时读取 |
| `content/<library-id>/blobs/` | 没有独立文件的字节数据，以 SHA-256 命名。目前仅包括从 PDF 中提取的插图 | 引擎在摄取时写入 | 引擎在嵌入插图时读取 |
| `uploads/<library-id>/` | 你摄取的文件。**对于视频、图像或音频文件，这里存放的就是资产本身**，而不是暂存副本 | 引擎，当 `assets.sh` 或其他客户端通过 API 上传文件时写入 | 引擎：摄取、嵌入和描述生成都直接在此打开文件 |
| `milvus/{etcd,minio,db}` | Milvus 元数据、段文件和本地数据 | Milvus 容器（compose 绑定挂载） | 仅 Milvus |
| `nebula/` | NebulaGraph 的数据和日志（启动后才有） | Nebula 容器 | 仅 Nebula |
| `models/` | 嵌入、重排、版面分析、ViCLIP、Whisper 和 GME 模型包 | 你，按照[如何准备模型](如何准备模型.md)操作 | 引擎加载模型时读取 |

视频、图像或音频文件不会被复制到内容存储中。其块通过 `file://` 路径指向该文件，引擎会打开该路径
进行嵌入和描述生成。因此，只要资产存在，`uploads/` 中的文件（或你提供的绝对路径上的文件）就必须保持原位。
如果移动或删除该文件，重新索引和描述生成将失败，并报错 `origin file is gone`。

删除资产时，若文件位于 `uploads/` 内，则会一并删除该文件。对于你指向其他位置的文件，引擎从不删除；`assets.sh delete` 的响应会在 `files_kept` 下列出这些文件（`delete-one` 不返回响应体）。
